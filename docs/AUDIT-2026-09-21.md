# Foster Guide — live-site and source audit

Date: 2026-09-21 (UTC). Auditor: Codex. Site: https://fosterguide.org/.
Source baseline: `5b30842` on `main`. This is an audit, not a deployment or implementation checkpoint.

## Verdict

Keep the preview designation. The visual foundation is clear and the directory and a sample Nova conversation work, but several reproducible defects affect access to help, plan creation, and trust. Address the P1 findings before expanding public use. No evidence of a production account compromise was found; this was not a penetration test or a clinical/legal certification.

The most urgent fixes are contact actions, crisis text destinations, verification claims, safety triage, the Food/Work intake failure, age filtering, and the emergency dialog's keyboard behavior. Security-sensitive source findings below need isolated regression tests and independent review before fixes are accepted.

## Coverage and evidence

- Live browser: desktop homepage/directory/detail; 390px mobile Ask, crisis panel, directory/detail, all six intake questions, Saved empty state, Privacy clearing prompt, partner landing/sign-in; 320px homepage. Temporary viewport overrides reset.
- Live interactions: directory search and no-results recovery; opening/closing listing details; Nova's built-in trade-school scholarship prompt; optional intake steps and a Food-only plan submission; privacy clearing prompt without confirming deletion or setting credentials.
- Public API: all 403 unique published listings, fetched in five pages; health; unauthenticated partner-account and session-export checks.
- Public HTTP: root, `/resources`, HTTP-to-HTTPS and www redirects, frontend and API response headers.
- External-link sample: all listings marked crisis plus Housing and Scholarships, 64 listings total, four concurrent read-only checks. This checks HTTP reachability, not program eligibility or available beds.
- Source: routing, directory filtering, contact rendering, intake, AI grounding/triage, privacy/export, partner auth/reset/change publishing, styling, deployment and operational documentation.
- Local validation: backend build and 76 tests passed in the first run; one integration test was blocked from opening localhost by the sandbox. That isolated partner-access test passed when rerun with localhost permission. Therefore all 77 backend tests passed across these runs. Frontend type-check and production build passed. Frontend Vitest: **3 skipped, 0 active tests**.
- Production dependency audit: frontend 5 affected packages (2 high, 3 moderate); backend 3 affected packages (moderate). These are package findings, not proof that each vulnerability is exploitable in the deployed application.

No real accounts, listings, reports, passwords, or permissions were changed. A generic scholarship prompt was sent to Nova using the audit browser's anonymous session. The synthetic Food-only plan failed validation before persistence. No successful plan, bookmark, or partner account was created. No crisis line was called or texted.

## Findings to fix first

P1 = fix before broader public use. P2 = important follow-up or launch requirement. Evidence distinguishes live observations, local reproductions, and source-only risks.

### A01 · P1 · Contact strings become invalid or inappropriate telephone links

**Confirmed live and in source.** Search for Crisis Text Line and open its detail on mobile: the primary action is **Call**, with `tel:741741`. This is a text service. National Safe Place's field similarly becomes a call to `44357`. Listing #92 has `phone = "Call 211 or text HOPE to 20121"`; stripping non-digits produces `tel:21120121`, combining two destinations into one invalid number.

`frontend/src/components/resources/ResourceRow.tsx:93` strips all non-digit/non-plus characters, and line 198 always emits `tel:`. The emergency dialog has the opposite problem: its text-only action is a styled `span`, not a link (`CrisisBar.tsx:90`).

**Fix:** structured call number, text number, text keyword and email fields; validate each independently and render Call/Text/Email actions. Migrate mixed strings. Test #412, #359 and #92 on Android/iOS and keyboard navigation. [Crisis Text Line's own instructions](https://www.crisistextline.org/text-us/) specify texting HOME to 741741.

### A02 · P1 · Crisis SMS destinations disagree with current provider instructions

**Live/source plus official-source comparison.** The emergency panel and both compiled crisis lists say California Youth Crisis Line: `Text 20121`, and National Runaway Safeline: `Text 66008`.

The [California Coalition for Youth](https://calyouth.org/cycl/) currently publishes 800-843-5200 for calls/texts. The [National Runaway Safeline get-help page](https://www.1800runaway.org/youth-teens/get-help) currently directs texts to 1-800-786-2929. Older materials contain 66008, so this audit does not assert that the old code is disconnected. It does establish that the app does not match the current contact instructions.

**Fix:** confirm destinations with providers, update frontend/backend together, and record evidence/date/owner. All six backend crisis contacts still have `verifiedOn: "UNVERIFIED"`. A human verification process remains outstanding; web checks do not count as phone verification.

### A03 · P1 · “Checked by phone” is inferred rather than evidenced

**Confirmed live/source.** All 28 crisis listings return `checkedHow: "phone"`. The API infers this using `/phone|line confirmed|called/` against `verified_by` (`backend/src/server.ts:195`). The importer writes `Foster Connect research (crisis line confirmed 2026-09-08)` for researched crisis entries (`data/build_resources.py:440`). Thus “line confirmed” alone creates a phone-check badge, including for text-only Crisis Text Line.

This does not prove nobody ever called a provider. It proves the implementation cannot substantiate the specific verification method it displays. The importer also marks extracted records `verified`, and any reviewer edit resets the entire listing's verification date even if only its title/region changed (`server.ts:1415`).

**Fix:** explicit verification method and field-level evidence, reviewer, date and next-review owner. Separate administrative edits from re-verification. Use “source reviewed” or “details not confirmed” when that is all the evidence supports. Remove global claims that everything was checked by a person until the records substantiate them.

### A04 · P1 · Safety triage suppresses plausible threats and misclassifies ordinary requests

**Local reproduction against freshly compiled code.** `assessSafety` returned:

| Synthetic input | Actual result |
| --- | --- |
| My dad will kill me if I tell anyone | none |
| my mom will kill me, she said that about my brother | none |
| I need to refill my pills tonight | crisis: suicide |
| I want to die | crisis: suicide |
| I have nowhere to sleep tonight | crisis: homeless_tonight |

The parent-threat idiom regex uses a broad lookahead for words such as “if” or “about” (`safety.ts:91`). It deletes threatening language as figurative. The means-plus-intent rule treats “pills” plus “tonight” as suicide intent, even for a refill request.

**Fix:** narrow idiom handling; preserve uncertain threats as at least concern; avoid inferring self-harm from a medication/time combination alone. Add these regressions and a larger evaluation set reviewed by qualified people. Existing passing tests do not cover these cases. No synthetic crisis disclosures were sent to production.

### A05 · P1 · Food-only and Work-only plans fail after six questions

**Food case confirmed live; Work follows the same source path.** Select Food, leave housing/documents/deadlines unanswered, select “I'm not sure yet,” select Alameda, then Build my plan. The app returns:

`Please check the information you entered (currentNeeds: String must contain at least 5 character(s))`

The UI accepts one chip, but the payload is `currentNeeds: "Food"`; the backend requires five characters (`server.ts:480`). “Work” is also four characters. This fails late, and the toast exposes an internal field name rather than a useful correction.

**Fix:** validate structured needs consistently; accept supported selections independently of their display-label length. Add end-to-end Food and Work tests with skipped optional answers. Keep errors persistent and actionable.

### A06 · P1 · Age bands hide listings relevant to people inside the selected band

**Source and complete live-data analysis.** The UI maps Under 18→17, 18–20→19, 21–24→22, 25+→26 (`ResourcesPage.tsx:44–50`); the API filters by that one age. Compared with an age-range-overlap query, this omits 2, 3, 18 and 12 listings respectively in the current catalog.

Examples: selecting 21–24 drops Alameda ILP (#126), whose stored maximum is 21; selecting 25+ drops Chafee (#292), whose stored maximum is 25. These examples establish inconsistency with the site's own data, not independent confirmation of actual eligibility.

**Fix:** range intersection, or ask exact age. Unknown age bounds must remain explicitly unknown, not become an eligibility promise. Test every boundary against stored min/max values.

### A07 · P1 · Emergency dialog does not manage keyboard focus

**Live DOM and source.** Opening “Need help now” leaves focus on the trigger outside the `aria-modal` dialog. The underlying page remains available in the accessibility tree; the custom dialog implements Escape/backdrop dismissal but no focus movement, trap, or background inertness.

**Fix:** use the project's accessible dialog primitive, place initial focus on its heading/close control, contain Tab navigation, and restore trigger focus on close. Verify keyboard and a real screen reader. Also make text-support controls real links (A01). This is an accessibility defect on the most time-sensitive journey.

### A08 · P1 · Privacy and trust statements conflict across pages

**Live/source.** Desktop Ask says “Nothing here is tied to your name” and “Conversations stay in this browser,” while the Privacy page correctly explains that messages pass through the server to an AI provider and entered information may identify someone. Saved says listings are kept in the browser, but they are stored server-side under a browser session. Partner landing says youth plans/chats/saved lists are “never visible to anyone,” an overly broad statement for a server-backed system. The mobile Ask layout hides the longer explanatory aside.

The crisis panel also says “All free, all confidential,” and deterministic homeless support promises lines help find a bed the same night. Confidentiality has service-specific limits and a referral cannot establish bed availability. [Crisis Text Line's FAQ](https://www.crisistextline.org/about-us/faq/) explicitly describes safety/legal exceptions and possible carrier charges.

**Fix:** consistent plain-language storage and AI disclosure beside the chat input at every breakpoint; describe who has application access without absolute guarantees; distinguish referrals from availability; use provider-specific privacy wording. Publish actual retention/deletion and provider information after checking deployment settings.

### A09 · P1 · Listing edits and search-index updates are not atomic

**Source-confirmed failure/concurrency risk; not fault-injected in production.** `applyResourceChanges` (`server.ts:1399`) separately deletes the FTS entry, updates the resource and reinserts FTS through three individual serialized calls. The proposal/audit/status changes are separate again. A failure or interleaving edit can leave the listing and search index inconsistent. The proposal approval path also reads “pending” before a later unconditional update.

**Fix:** one transaction covering a conditional proposal claim, resource update, FTS and audit writes, with rollback/failure/concurrent-review tests. Reuse the proven transactional pattern in `services/persistence.ts`. Sequential happy-path partner tests do not establish atomicity for this newer edit path.

## Important follow-up findings

### A10 · P2 · Skipping documents is treated as having no documents

**Browser/source.** Question 3 permits Next with no selections. It sends `documents: []`, and `ai.service.ts:447–452` explicitly converts the complement into `documentsTheyAreMissing`; the fallback also creates replacement-document tasks. “Prefer not to say,” “not sure” and “none” are indistinguishable.

**Fix:** capture unknown/declined separately; only generate replacement steps for explicitly missing items. The homepage's “Questions are optional” also overstates the flow: a need, future response and county are required.

### A11 · P2 · Password reset consumption is vulnerable to concurrent reuse

**Source-only concurrency risk.** `/api/partner/reset` selects an unused token, hashes/updates the password, marks the token used, then removes sessions in separate statements (`server.ts:1570–1582`). Two simultaneous requests can pass the initial check; a later failure can leave a changed password without session revocation. The existing test covers sequential reuse only.

**Fix:** atomically claim/consume the token with the password change and session revocation. Add simultaneous reset and injected-failure tests in a disposable database. When email is enabled, also test consistent responses for existing/nonexistent accounts: the current successful-mail and fallback response texts differ.

### A12 · P2 · Automatic recovery email is not configured live

**Live health evidence.** `/api/health` returned `mailConfigured: false` and `aiConfigured: true`. Reset therefore uses the manual-reviewer path; a successful UI request is not proof an email was sent. A locked-out sole reviewer still requires an operational recovery route.

**Fix:** configure and verify the mail provider/domain, test delivery to an authorized test account, and document backup reviewer recovery. Do not claim this audit tested delivery.

### A13 · P2 · Resource metadata is too incomplete for strong matching claims

**Complete 403-record public snapshot.**

| Measure | Count |
| --- | ---: |
| No structured languages | 403 |
| No structured accessibility information | 403 |
| No hours | 370 |
| No numeric age bounds | 326 |
| No phone/contact string | 144 |
| Eligibility begins with “Not confirmed” | 160 |
| Cost contains “Not confirmed” | 233 |
| Organization equals listing title | 349 |
| No explicit next-review date | 401 |

Missing phones/hours can be appropriate for guides or email-only services; these counts are triage measures, not 403 individual errors. Some descriptions contain details missing from structured fields. “By organization” often behaves like title sorting. Shelter listings can show “Online” because delivery mode was inferred from a website; Covenant House Oakland does so live. Similar FURS/Runaway/Covenant listings need provider-level deduplication rather than being assumed distinct services.

**Fix:** prioritize crisis/housing contacts and hours, then eligibility, language and accessibility; distinguish unknown from not applicable; track organization and program separately. Validate the inferred delivery modes and duplicate candidates.

### A14 · P2 · Verification dates have insufficient text contrast

**Live computed styles and calculation.** The 12px `.text-stamp` uses `#8A857A` on `#F4F2ED`, giving **3.28:1** contrast. It is normal-size text, below the [4.5:1 WCAG AA threshold](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html). This is the date/method evidence people are asked to trust.

**Fix:** darken the stamp token to at least 4.5:1 on every used surface; verify both accents and states. This was a targeted check, not a complete WCAG conformance assessment.

### A15 · P2 · Mobile partner pages hide the route back to the youth site

**Live at 390px/source.** The only Youth site header link is `hidden ... sm:inline-flex` in `PartnerLayout.tsx:45`. The brand links back to `/partners`; the signed-out mobile landing/sign-in has no visible direct youth-home link. During navigation from a scrolled Privacy page to Home, Home also appeared partway down until scrolled to top.

**Fix:** keep a youth-site return action visible on mobile; set intentional scroll behavior for fresh route navigation while preserving Back history where appropriate. Test after scrolling long pages.

### A16 · P2 · “Clear this device” leaves personal preferences and abandoned server records

**Source and live disclosure.** `clearDeviceData` removes session and chat keys but leaves homepage age/county/care preferences. The Privacy page acknowledges this, but the action name and shared-device flow still require a second clearing step. Clearing without a passcode abandons server records; no automatic expiry/retention job was found. The success toast always says a passcode opens the plan again, even when the user chose no passcode.

**Fix:** offer one comprehensive device-clear action, give accurate branch-specific confirmation, and define server retention for abandoned anonymous sessions. Explain backup/provider deletion limits instead of implying deletion erases all copies everywhere. Actual backup/provider policies were not available to verify.

### A17 · P2 · Deep links return HTTP 404; production is intentionally non-indexable

**Live HTTP/source.** `/` returns 200. `/resources` returns HTTP 404 with the app shell; browser JavaScript still renders the directory. GitHub Pages is serving the copied `404.html` as the SPA fallback. The live head contains `noindex, nofollow`; the workflow explicitly sets `VITE_PREVIEW=1`.

**Fix at public launch:** use hosting/routing that returns 200 for genuine application routes, retain real 404s for unknown paths, and deliberately remove preview indexing restrictions when ready. Add route-specific titles/descriptions, canonical URLs, a sitemap and a social preview image. Do not remove noindex merely to improve an audit score while launch blockers remain.

### A18 · P2 · Individual resources cannot be shared or reopened by URL

**Live/source.** Opening a resource only changes local component state; the address remains `/resources` with the search query. There is no public detail route in the router. Sharing the page does not preserve the chosen listing.

**Fix:** stable listing URLs or a resource-ID query parameter with direct-load support and back/forward behavior. This materially helps caseworkers share one program with a young person.

### A19 · P2 · Dependency updates and frontend document security need a pass

**Package audit and headers.** `npm audit --omit=dev` reports frontend `js-yaml`/`nanoid` high findings and `@humanfs/node`/`@vitest/mocker`/`vitest` moderate findings; backend reports `qs` and affected `express`/`body-parser` dependency paths as moderate. Frontend tooling is largely declared under dependencies, so production-classified audit results do not imply that all vulnerable code ships in browser JS. The backend `qs` advisory does affect a runtime dependency path; exposure still needs assessment.

The API supplies Helmet/CSP/HSTS and other headers. The HTML document served by Pages did not supply CSP, frame protection or an explicit referrer policy. API headers do not protect the frontend document.

**Fix:** update lockfiles with compatible patched versions, review the Vitest major-version change, put tooling in devDependencies, and verify actual reachability. Add frontend CSP/frame/referrer protections using appropriate hosting support; self-host fonts if desired. No dependency changes were made.

Advisories: [js-yaml](https://github.com/advisories/GHSA-2883-xcg3-v3hh), [nanoid](https://github.com/advisories/GHSA-2v37-7h3g-55p8), [Vitest](https://github.com/advisories/GHSA-82fw-gwwq-j7x9), [humanfs](https://github.com/advisories/GHSA-p498-v437-472g), [qs](https://github.com/advisories/GHSA-4mjr-xmp4-gh2g).

### A20 · P2 · Automated assurance and operational readiness are incomplete

**Local tests/source/docs.** There are no active frontend tests. The only checked-in workflow is frontend deployment; it type-checks/builds but does not run backend tests or journey tests. `/api/health` returns a constant status plus configuration flags and performs no database query. It can stay green while core data is unavailable. Deployment docs still identify no uptime monitoring and a required Turso restore drill; no evidence of a completed restore was available.

**Fix:** CI gates for backend and key youth/partner journeys, accessibility checks, separate liveness/readiness checks, a resource-query synthetic monitor, and a documented tested backup restore. Measure real-user performance separately; this audit did not obtain Lighthouse or field Core Web Vitals.

## What worked

- Desktop homepage hierarchy and the 320px homepage were readable; measured page width equaled viewport width. The 390px resource detail also had no horizontal page overflow.
- The directory returned 403 unique listings with pagination; text search produced results and an explicit useful no-results state.
- The live scholarship prompt produced a readable Nova response and three directory cards, including Fostering Wishes. This is one sample, not an AI accuracy evaluation.
- Source-backed AI fallback, contact sanitization, signed history, transactional initial publishing and plan persistence have passing local tests.
- Live partner accounts endpoint rejected unauthenticated requests (401); session export without a session was rejected (400). Local partner integration checks cover contributor/reviewer boundaries, ownership, logout, access removal and sequential reset reuse.
- Privacy visibly distinguishes device clearing and server deletion and warns about shared browsers. The passcode-first prompt opens correctly; no credentials were entered.
- HTTPS and www redirects lead to the canonical HTTPS root. API security headers were present.
- Route-level code splitting exists; the PDF library is dynamically loaded. Local main JS build was about 412KB raw/129KB gzip and CSS 114KB raw/19KB gzip. These are local build measurements, not live speed scores.

## Recommended sequence and acceptance checks

1. **Access to urgent help:** A01–A04 and A07. Confirm provider channels, repair call/text controls, replace inferred verification badges, fix triage regressions and modal focus. Human review plus mobile dial/SMS tests; do not place test calls to emergency services.
2. **Core youth journeys:** A05, A06, A10. A Food-only plan and Work-only plan must save; skipped information stays unknown; age-band boundary programs remain discoverable. Verify fallback and successful AI paths, edit/save/reload, and PDF export with synthetic fixtures.
3. **Privacy and data integrity:** A08–A09, A11–A12, A16. Align disclosures, test atomic edits/reset concurrency, configure authorized test mail and exercise two-device clearing/recovery/deletion against isolated data. Independent review required for these fixes.
4. **Directory and usability:** A13–A15, A18. Assign data owners, contrast fixes, mobile navigation and sharable resources.
5. **Launch/operations:** A17, A19–A20. Update dependencies, test CI/restore/monitoring, then handle indexing and hosting status codes when public launch is approved.

## Explicit limits

Authenticated live reviewer/contributor screens were not opened: no test credentials were supplied. Local API integration tests are not a substitute for that browser sign-off. Live reset email, credential changes, passcode recovery, destructive deletion, successful plan persistence/editing, populated Saved and PDF output were not tested end-to-end in this audit. The failed Food journey is recorded rather than presented as a successful plan test.

No real screen-reader session, physical iOS/Android dial/SMS test, full automated accessibility scan, load test, offline simulation, provider privacy-contract review, production log/cloud-configuration inspection, backup restoration, or comprehensive AI evaluation was performed. Content counts cover every published listing; real-world service accuracy was checked only for the specifically cited provider instructions. All other source-only risks are labeled. Existing older audits are historical; this report does not imply every item in them remains open.
